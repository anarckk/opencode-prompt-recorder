opencode-prompt-recorder 功能设计

OpenCode 插件 —— 自动记录用户提示词到本地文件系统

一、概述

opencode-prompt-recorder 是一个为 OpenCode AI 编程助手设计的插件，核心功能是自动捕获并持久化用户在聊天对话中发送的提示词到本地文件系统。它作为审计日志、训练数据收集和会话历史工具，无需用户任何手动操作即可后台静默运行。

💡 项目地址： https://github.com/anarckk/opencode-prompt-recorder  |  版本：1.8.0  |  作者：anarckk  |  许可：MIT

功能特性

📥 自动捕获

  • 被动监听：订阅 OpenCode 的 message.part.updated 事件，用户发送提示词后自动保存，无需手动操作
  • 角色过滤：仅记录 role === "user" 的消息，忽略 AI 回复和系统消息。通过四级 fallback（messageRoleMap → part.message.role → info.role → info.message.role）适应 OpenCode 版本差异
  • 多级内容过滤：跳过 synthetic 部件（其他插件注入的系统提示）、ignored 部件（仅用户可见的通知）、<system-reminder>/<system> 标签包裹的系统注入内容
  • 消息去重：以 messageID + text 组合键去重，防御并发事件和消息内容不变的极端情况

📁 文件存储

  • 时间目录：按 .agent/prompts/yyyy/MM/dd/ 分层存储，日期一目了然
  • 会话合并：同一会话的多条消息合并到同一个文件，避免碎片化。首条消息创建文件，后续消息追加写入
  • Task 子会话分离：task 工具创建的子 agent 会话的提示词自动存入 .agent/prompts/task/yyyy/MM/dd/ 目录，与主会话隔离
  • 文件名格式：yyMMddHHmm-{主题}.txt，主题优先取自会话标题；标题不存在时回退到首条消息文本。若文件创建后标题才到达，文件自动重命名匹配标题（session.updated 事件 + 待处理队列 + 5 秒 SDK 查询兜底）
  • 文件名净化：移除 <>:"/\|?*、控制字符、Unicode 控制字符（零宽空格/BOM/方向覆盖等）、HTML 标签，截断至 40 字符，空白时回退为 untitled
  • 缓存写入：sessionFileCache 缓存文件路径，避免重复目录计算和 IO 开销
  • 跨天支持：每条消息的时间戳包含日期（yyyy-MM-dd HH:mm:ss），目录按首条消息日期决定

🏷️ 会话标题

  • 实时捕获：监听 session.created 和 session.updated 事件，将 event.properties.info.title 存入 sessionTitleMap
  • 文件名优先：创建文件时优先用会话标题作文件名；标题不存在时回退到首条消息文本。若文件创建后标题才到达，自动重命名文件（事件先于文件创建的竞态通过待处理队列解决，5 秒后 SDK 查询兜底修正）

🔄 自动更新

  • 版本检查：插件启动时异步查询 npm registry，获取最新版本号
  • 自动升级：发现新版本后删除旧版本目录，依赖 npm 重启时重新安装
  • 模块级互斥：通过 autoUpdateChecked 标志防止多插件实例重复检查
  • 用户通知：更新后 5 秒通过 TUI Toast 提示用户重启

🛡️ 可靠性

  • 错误静默：所有异常被捕获并静默处理，不干扰 OpenCode 正常运行
  • 版本化 Readme：插件启动时自动写入 .agent/opencode-prompt-recorder-readme.txt，记录版本和项目信息
  • 调试日志：设置 PROMPT_RECORDER_DEBUG=1 环境变量后，详细日志写入 .agent/prompts-log/log.txt

⚡ 使用场景

  • 审计追踪：完整记录每一次与 AI 的交互过程，便于事后回溯
  • 训练数据收集：积累真实用户提示词，可用于模型微调或 prompt 工程优化
  • 会话历史：对话按时间组织，便于回溯
  • 质量监控：记录用户提问模式，分析使用趋势

二、功能设计

2.1 设计目标与原则

插件的设计围绕以下核心目标展开：

目标优先级说明
零配置P0安装即用，用户无需任何配置即可开始记录
零侵入P0不干扰 OpenCode 正常运行，不修改用户数据
数据安全P0不联网，所有数据仅存本地文件系统
可靠性P1不丢消息，不重复记录
可读性P2存储格式直接可读，无需工具解析
最小依赖P1零运行时依赖，仅 peer dependency

设计原则：

  • 简单至上：能用 Map 不用数据库，能单文件不拆分模块
  • 被动监听：不主动轮询，完全依赖 OpenCode 事件驱动
  • 快速失败：前置条件不满足时立即返回，不执行不必要的 IO
  • 防御性编程：对事件 payload 做多层 fallback 解析，适应 OpenCode 版本变化

2.2 需求分析

功能需求

ID需求说明
F1自动捕获用户发送提示词后自动保存，无需手动操作
F2按时间组织文件按 yyyy/MM/dd 目录分层，文件名包含时间戳
F3会话聚合同一会话的多条消息合并到同一文件，以会话标题命名；标题不存在时回退到首条消息文本
F4角色过滤仅记录用户消息，忽略 AI 回复和系统消息
F5去重同一消息不被重复保存
F6文件名净化特殊字符自动清理，防止文件系统错误
F7系统内容过滤跳过他方插件注入的系统提示
F8Task 子会话分离task 工具的子 agent 提示词存入独立目录

非功能需求

ID需求约束
NF1性能单次 IO < 10ms，不阻塞事件循环
NF2兼容性支持 OpenCode v0.15.0+，Node.js ≥18 / Bun
NF3零依赖运行时无 npm 依赖，降低供应链风险
NF4跨平台Windows / macOS / Linux 文件路径兼容

2.3 方案选型与权衡

以下是关键设计决策的选型分析：

决策 1：单文件 vs 多模块

单文件（选中）多模块拆分
优点零模块加载开销；重构时全局可见；引入简单关注点分离；便于单元测试
缺点函数间隐式耦合需要模块间接口定义；构建产物膨胀
结论代码 ~220 行，拆分反而增加心智负担。单文件更适合小型插件

决策 2：闭包模式 vs Class

函数闭包（选中）Class 实例
优点与 Plugin 工厂函数自然匹配；无 this 绑定问题更熟悉的面相对象模式
缺点不支持继承扩展需要 new 实例化，与 Plugin 类型签名不完全匹配
结论闭包模式是 OpenCode 插件系统的首选，也是官方示例采用的风格

决策 3：文件系统 vs 嵌入式数据库

文件系统（选中）SQLite / LevelDB
优点零外部依赖；任何编辑器可直接查看；目录结构天然可浏览结构化查询；高效全文检索
缺点不具备查询能力；大规模文件时性能下降引入数百 KB 原生依赖；破坏零依赖原则
结论数据量级（每日数十条文本）不需要数据库。可读性优先于可查询性

决策 4：单一事件处理器 vs 多个独立钩子

统一 event 钩子（选中）多个独立钩子（message.updated 等）
优点状态共享在同一闭包作用域；减少注册代码职责清晰；每种事件独立处理
缺点一个函数内处理所有事件类型，体量增大需要跨钩子共享状态（通过 ctx 或外部变量）
结论事件类型仅 4 种，统一处理器足够简洁。若扩展到 10+ 事件类型则应拆分

决策 5：会话合并 vs 每条消息独立文件

同会话合并（选中）每条消息独立文件
优点文件数与会话数正相关，而非消息数；一次会话一个文件，便于回溯实现简单；无状态
缺点需要 sessionFileCache 维护状态；并发追加有竞态风险碎片文件多；翻阅困难
结论一次对话通常包含 5-20 条消息，合并后降低碎片化，提升可读性

决策 6：消息去重 key 设计

messageID + text 组合（选中）仅 messageID
优点防御 messageID 不变但内容变化的极端情况更少的字符串拼接
缺点key 较长；增加内存占用假设 messageID 全局唯一且内容不变
结论组合 key 更保守。内存开销可忽略（单个 key < 1KB）

决策 7：Task 子会话识别策略（迭代演进）

v1：mainSessionId 比较（已废弃）v2：ToolPart metadata 追踪（当前）
原理首条用户消息的 session 为 "主会话"，不同的视为 task监听 task 工具 ToolPart 的 metadata.sessionId
问题新对话 session 变化后被误判为 task依赖 metadata 到达时序，但实践经验中可靠
结论v2 方案与 OpenCode 自身追踪子 session 的方式一致（subagent-data.ts:316-339），更精准

2.4 被拒绝的替代方案

方案拒绝原因
SQLite 存储引入原生依赖，破坏零依赖原则；增加构建复杂度
JSON / YAML 格式不如纯文本直接可读，需要额外工具查看
轮询式数据采集违背 OpenCode 插件的设计规范（应被动监听）
网络上报（中心化收集）数据安全不可接受；用户期望数据存本地
通过 chat.message 钩子拦截会修改消息流，违背零侵入原则。改用 message.part.updated 只读监听
正则解析角色（从消息内容推断）不可靠。改用事件的 role 字段 + 多层 fallback

2.5 错误处理策略

场景策略
目录创建失败异常传播到事件循环，OpenCode 自动重试
文件写入失败同上
package.json 读取失败版本回退为 "unknown"
readme 文件写入失败静默忽略，不影响主功能
debug log 写入失败console.error 报告，不抛异常
事件 payload 缺少字段多层 fallback 逐级尝试，全部失败则跳过
synthetic / ignored 部件误入主动跳过，避免记录非用户内容

2.6 边界情况处理

场景处理方式
空文本提示词跳过，不写入
纯空白 / 特殊字符文件名回退为 "untitled"
超长标题 / 提示词（>40 字符）截断至 40 字符作为文件名；标题为空时回退到首条消息文本
系统注入标签（海马体等）isSystemInjected() 检测并跳过
并发消息事件通过 processedMessageKeys 去重
跨天会话时间戳含日期（yyyy-MM-dd HH:mm:ss），按首次消息日期分目录
消息包含 HTML 标签sanitizeFilename 剔除 <...>
Windows 非法文件名字符正则替换 <>:"/\|?* 及控制字符
插件进程重启去重 Set 清空，但文件追加写入不会产生重复
OpenCode 版本升级导致事件结构变化四级 role fallback 保持兼容

三、架构设计

插件采用事件驱动 + 函数式闭包的架构模式。整个插件是一个符合 @opencode-ai/plugin 的 Plugin 接口的工厂函数，内部使用 JavaScript 闭包来维护运行时状态。

3.1 事件驱动模型

插件注册一个统一的 event 异步处理器，监听四种事件类型：

事件类型触发时机处理动作
message.updated消息元数据更新时提取 messageID to role 映射存入 Map，供后续事件使用
message.part.updated消息内容部分更新时核心逻辑：检测 task、检查 role、去重、按 session 缓存写入或追加
session.created会话创建时捕获会话标题存入 sessionTitleMap，若有缓存文件则重命名以匹配标题
session.updated会话更新时捕获标题变更，文件自动重命名匹配新标题（若文件未创建则暂存待处理）
sequenceDiagram
    participant OC as OpenCode Runtime
    participant PR as Plugin
    participant FS as File System

    OC->>PR: message.updated
    Note over PR: cache role map

    OC->>PR: message.part.updated (type=text, role=user)

    else subsequent messages

    OC->>PR: message.part.updated (type=tool, tool=task)
    Note over PR: track child sessionId

    OC->>PR: session.created
    Note over PR: capture session title

    OC->>PR: session.updated
    Note over PR: capture title change + write readme

3.2 核心数据流

一次完整的用户提示词录制过程：

flowchart TD
    E[message.part.updated] --> T{part.type?}
    T -->|tool + task| M[提取 metadata.sessionId]
    M --> S[加入 taskSessionIds Set]
    T -->|text| F{role === user?}
    F -->|No| Skip[跳过]
    F -->|Yes| Sys{synthetic/ignored?}
    Sys -->|Yes| Skip
    Sys -->|No| Inj{isSystemInjected?}
    Inj -->|Yes| Skip
    Inj -->|No| D{已去重?}
    D -->|Yes| Skip
    D -->|No| C{有缓存文件?}
    C -->|No| N[创建新文件]
    C -->|Yes| A[追加到现有文件]
图 2：消息处理决策流

关键设计决策回顾（详见 2.3 节）：

  • 仅录制用户消息：通过 role === "user" 过滤，忽略 AI 回复和系统消息
  • 快速失败：前置条件不满足时立即返回，不执行文件操作
  • 延迟写入：先做所有检查和查找，最后一次性写入
  • 会话缓存：sessionFileCache 避免重复目录计算和 IO
  • 会话标题文件名：通过 session.created/session.updated 事件捕获标题存入 sessionTitleMap，文件创建时优先用标题；标题不存在时回退到首条消息文本。若文件创建后标题才到达，自动重命名文件。事件到达早于文件创建的竞态场景通过待处理队列 + 5 秒 SDK 查询双层兜底
